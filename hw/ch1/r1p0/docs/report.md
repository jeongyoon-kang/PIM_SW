## 1. 확인된 것 `[실측 2026-08-10]`

### 1.1 GB 를 채우는 두 경로가 같은 답을 낸다

MAC 은 벡터를 **Global Buffer** 에서 받는다. GB 를 채우는 길이 둘 있고,
`emu_gemv --fill both` 가 둘을 연속으로 돌려 lane 단위로 대조한다.

| 경로 | word 0 | 벡터가 놓이는 곳 |
|---|---|---|
| WRVEC | `ISR_WRVEC` `ROW`=GPR word | GPR (호스트가 DMA 로 적재) |
| COPY | `ISR_COPY` `ROW`=DRAM row, `route[0]=16`(GB) | bank 0 의 DRAM row |

두 프로그램은 **word 0 하나만 다르다** — MAC·RD_MAC·EOS 가 동일하다. 그래서
lane 이 일치한다는 것은 fill 경로 말고는 차이가 없다는 뜻이다.

```
=== fill = WRVEC ===   16/16 ok, 14 us
=== fill = COPY  ===   16/16 ok, 20 us
WRVEC vs COPY: all 16 lanes identical
```

**`ISR_COPY` read-half 가 하드웨어에서 처음 동작했다.**

> **덤 — GB flush 질문.** 가이드 §6 은 WRVEC 이 GB 를 flush 한다고 적었고 §5 의
> COPY 에는 그 언급이 없다. WRVEC 직후 COPY 를 돌렸는데 COPY 가 정확했으므로
> **잔여물 문제는 없다.** flush 때문인지 앞 MAC 이 다 소비해서인지는 구분되지 않는다.

### 1.2 `ISR_EWMUL` 이 동작한다 — 처음

가이드 §4 의 조 구성(`실행 i`, `먹임 s: route[s]=i`, `목적지 d: route[i]=d`,
`pu_mask=1<<i`, `gb_mc_mask=0`)을 그대로 인코딩해 `emu_ewmul` 로 확인했다.

MAC 과 달리 **누산하지 않고 결과를 제3 뱅크의 DRAM 에 쓴다.** 그래서 RD_MAC 도
GPR 도 쓰지 않고 **직접 창 되읽기**가 검사다. 프로그램은 `EWMUL` + `EOS` 두 워드다.

| 실행 | 결과 |
|---|---|
| feed 2 → exec 3 → dst 1 (가이드 예) | 16/16 원소 일치, 17 us |
| `--sweep` — 16개 조 (feed n → exec n+1 → dst n+2) | **16/16 조 전부 통과** |
| `--l 4` (64 원소) | 64/64 일치 |

목적지를 poison 으로 채운 뒤 실행하므로 아무것도 안 한 EWMUL 은 poison 으로
되읽혀 잡힌다.

### 1.3 부분 `pu_mask` + RD_MAC 은 멈추지 않는다

가이드 §7 은 *"MAC 을 한 번도 안 돌린 뱅크가 하나라도 있으면 그 뱅크에서
멈춘다(hang)"* 고 경고한다. **부분 `pu_mask` 에는 해당하지 않는다.**

| `--pu` | MAC 실행 뱅크 | RD_MAC | 미참여 lane |
|---|---|---|---|
| `0xFFFF` | 16 | 정상, 4 us | — |
| `0x0001` | **1** | 정상, 20 us | `0x0000` |
| `0x8000` | **1** | 정상, 16 us | `0x0000` |
| `0x5555` | **8** | 정상, 14 us | `0x0000` |

세 경우 모두 첫 폴에 끝났다(`STATUS polls = 2`, `GPR reads = 1`). 리셋 상태의
latch 는 읽을 수 있고 `0x0000` 으로 걷힌다. **`0x5555` 가 통과하는 것이 중요하다**
— peer 소싱 GEMV 가 쓸 마스크다.

### 1.4 여러 ISR 이 한 프로그램 안에서 합성된다

`emu_gemv` 는 MAC 을 한 발만 쏜다. 프로그램이 4 워드보다 길어질 때 걸리는 규칙 넷을
`emu_chain` 으로 따로 물었다 — **넷 다 처음 확인됐다.**

| 프로브 | 프로그램 | 물음 | 결과 |
|---|---|---|---|
| `chain` | `WRVEC\|MAC\|MAC\|RD_MAC\|EOS` | 누산기가 ISR 을 건너 사나 | **통과** — 정확히 2 배 |
| `rewind` | `WRVEC\|MAC\|RD_MAC\|MAC\|RD_MAC\|EOS` | 한 WRVEC 이 MAC 여럿을 먹이나 | **통과** — 두 워드 모두 1 배 값 |
| `kchunk` | `WRVEC(1.0)\|MAC\|WRVEC(2.0)\|MAC\|RD_MAC\|EOS` | K 를 쪼갤 수 있나 | **통과** |
| `gemv` | `WRVEC` + G × `{MAC, RD_MAC}` + `EOS` | 커널 전체가 한 발에 되나 | **통과**, G = 2000 까지 |

`rewind` 가 특히 중요하다. 가이드 §3 이 "GB 읽기 포인터를 되감는다"고 적어두기만 한
것이고 아무도 실행한 적이 없었다. **참이다** — 그래서 GEMV 하나에 벡터 적재가
`N/16` 번이 아니라 **한 번**이면 된다.

### 1.5 규모와 처리량

전부 **한 번의 doorbell**, 전 출력 lane 대조.

| N | K | ISR | 시간 | GMAC/s | |
|---|---|---|---|---|---|
| 1024 | 1024 | 130 | 100 µs | 10.49 | PASS |
| 16384 | 1024 | 2050 | 1388 µs | 12.09 | PASS |
| 2048 | 4096 | 1029 | 698 µs | 12.02 | PASS |
| **32000** | **2048** | **8003** | **5334 µs** | **12.29** | PASS |

회귀하면 `T(µs) ≈ 14 + 1.37·C + G·C·(0.543 + 0.0128·L)`, G = 16~2000 에서 오차 2.5 %.

- **beat 당 12.77 ns.** 200 MHz 에서 2.55 사이클로 `T_CCD=2` 바닥에 가깝다.
  **이 값이 클럭 모호성을 지운다** — 150 MHz 라면 1.92 사이클이 되어 바닥 아래이므로
  불가능하다.
- **그룹당 고정비 543 ns** (RD_MAC + row activate). 64-beat MAC 의 유효 시간이
  819 ns 이므로 최대 OPSIZE 에서도 효율은 60 % 다.
- **64-beat WRVEC ≈ 1.37 µs** — MAC 보다 비싸다.

루프 순서를 바꾸면 (청크를 바깥으로) 벡터 적재가 `G·C` 회에서 `C` 회로 줄어
`N=2048, K=4096` 에서 1141 → 698 µs, **1.63 배**다.

가중치 업로드는 뱅크별 슬라이스를 **연속으로** 써야 한다 — row 마다 쓰면 64 row 에
13.9 ms (150 MB/s), 뱅크마다 한 번씩 쓰면 0.4 ms (최대 4097 MB/s) 로 **35 배** 차이다.

### 1.6 r0p0 의 결함 두 건이 r1p0 에서 해소됐다

r0p0 에서 미해결로 남았던 두 결함이 **재현되지 않는다.**

| 검사 | r0p0 | **r1p0** |
|---|---|---|
| `emu_mc --read --bank 4 --kib 32` | 3840/4096 워드 오류 (93.75 %) | **PASS** |
| `emu_mc --read --kib 32` (16 슬롯) | — | **PASS**, 순열 없음 |
| `emu_gpr_loop --mib 1 / --mib 4` | 128 B 블록 어긋남, 절반 오류 | **PASS**, 불일치 0 |
| GPR 대역폭 | 쓰기 713 / 읽기 612 MB/s | **쓰기 1978 / 읽기 909 MB/s** |

r0p0 의 결함은 `emulator_controller_0/s_axi` 가 `ARSIZE` 를 무시해 호스트가 256 B
를 요청했는데 512 B 가 실려오던 것이었고, GPR 되읽기도 128 B 블록 단위로
어긋났다. 둘 다 사라졌다.

**대역폭이 약 3 배로 뛴 것**이 폭 불일치가 해소된 것과 앞뒤가 맞는다 — 같은
전송에 실리는 유효 바이트가 늘었다.

### 1.7 산술 — 누산기 폭과 누산 순서

**둘 다 ch1 에서 직접 쟀다.** `bank_controller_top` 에도 같은 답이 있지만 그건
**뱅크 하나를 떼어내 CSR 인터페이스로 독립 실행한 DUT** 라, 이 실리콘도 이 명령
경로도 아니다. 넘겨받지 않고 다시 물었다.

**폭 — BF16 보다 넓다.** `w[0]=1.0`, `w[k>0]=2^-9`, `v=1.0`. 각 `2^-9` 는 진행
중인 합의 half-ulp 아래라, BF16 누산기라면 전부 버려지고 정확히 `1.0` 이 나온다.

| L | K | BF16 누산기라면 | 더 넓다면 | 디바이스 |
|---|---|---|---|---|
| 1 | 16 | `0x3F80` | `0x3F84` | **`0x3F84`** |
| 4 | 64 | `0x3F80` | `0x3F90` | **`0x3F90`** |
| 16 | 256 | `0x3F80` | `0x3FC0` | **`0x3FC0`** |
| 64 | 1024 | `0x3F80` | `0x4040` | **`0x4040`** |

**ISR 을 건너서도 넓다.** `MAC(1.0)` 뒤에 `MAC(2^-9)` 를 여덟 발 — BF16 로 좁아지면
여덟 번 다 반올림돼 사라져 `1.0` 이 나온다. 디바이스는 `0x3F82 = 1.015625` 로
`1 + 8·2^-9` 다. **K 를 쪼개 연쇄해도 폭을 잃지 않는다.**

**순서 — adder tree 가 아니라 순차다.** `[실측]`

무작위 데이터로는 판정이 안 된다. 출력이 BF16 8 비트뿐이라 fp32 순서 차이가 묻힌다
(현실 분포에서 모델끼리 갈리는 lane 이 **4096 중 1 개**). 그래서 **후보 모델들이
가까운 답이 아니라 아예 다른 답을 내도록** 벡터를 지어서 물었다 — tree 가 먼저 짝짓는
lane 에 `ε`, 나머지에 `±A` 를 두어 다른 짝은 정확히 상쇄되게 한다.

| 벡터 | 디바이스 | 배제되는 것 |
|---|---|---|
| 대조군 — `±A` lane 을 0 으로 | `0.03125` = 모든 모델의 예측 | `ε` 가 flush 되지 않는다 (아래 두 줄의 null 이 의미를 갖는 근거) |
| `ε` 를 lane 0,1 에 (adjacent 겨냥) | `0` | **adjacent tree `(2i, 2i+1)`**, K 전체 tree |
| `ε` 를 lane 0,8 에 (halves 겨냥) | `0` | **halves tree `(i, i+n/2)`** |

**표준 16-lane adder tree 배선 두 가지가 모두 배제되고, 순차 fp32 합이 모든 벡터에서
전부 일치한다.** 설계 의도(곱셈 lane → adder tree → MAC)와 어긋나므로, 트리가
균형 이진 트리가 아니라 **파이프라인 가산기 체인**일 가능성이 높다. 배선을 확인할
가치가 있다.

> 저장소의 모순이 이걸로 정리된다. `bank_controller_top/SW/pimemu.py` 가 적은
> "lane by lane 순차" 가 맞고, 같은 스택의 `run_qwen.py` 와 ch1 `emu_gemv.c` 가 적은
> "adder tree" 는 **틀렸다.** `run_qwen.py` 의 "0.02~0.07 % 행이 갈린다" 는 수치는
> 여기서 잰 0.024 % 와 같지만, 그건 **디바이스의 오차가 아니라 두 모델이 서로 갈리는
> 비율**이다. `emu_gemv.c` 의 `tree_sum` 은 `device_sum` 으로 고쳤다.

### 1.8 K 분할 스케줄 — 속도와 정확도의 교환 `[실측]`

`K > 1024` 는 반드시 `C = ceil(K/1024)` 개로 쪼개진다. 배치가 둘이다.

| | 벡터 적재 | RD_MAC | 반올림 |
|---|---|---|---|
| group-outer | `G·C` 회 | `G` 회 | 출력당 **1 번** |
| chunk-outer | **`C` 회** | `G·C` 회 | 출력당 `C` 번 (호스트가 부분합 합산) |

`N=1024`, 무작위 정규 피연산자, 기준은 K 전체에 대한 순차 fp32 를 한 번 반올림:

| C | K | group-outer | chunk-outer | 속도 |
|---|---|---|---|---|
| 2 | 2048 | **정확** 0/1024 | 26.8 % 가 1 ulp | 1.36× |
| 4 | 4096 | **정확** 0/1024 | 16.9 % 가 1 ulp | 1.38× |
| 6 | 6144 | **정확** 0/1024 | 8.9 % 가 1 ulp | 1.41× |
| 8 | 8192 | **정확** 0/1024 | 9.4 % 가 1 ulp | 1.43× |

- **group-outer 가 기준과 정확히 일치한다** — 연쇄가 폭을 안 잃는다는 §1.7 을 다시
  확인해 주고, 동시에 기준 모델이 맞다는 것도 확인해 준다
- **chunk-outer 의 오차는 어떤 C 에서도 1 ulp 를 넘지 않는다.** C 가 커질수록 오차율은
  오히려 **줄어든다** — 합의 크기가 커져 마지막 BF16 반올림이 지배하기 때문이다
- 속도 이득은 `G` 와 함께 커진다 (G=64 에서 1.4×, G=128 에서 **1.63×**). LLM 형상은
  G = 128~704 이므로 1.6× 쪽이 해당한다

읽히는 것: **평소에는 chunk-outer, 검증할 때는 group-outer.** 후자가 bit-exact 라서
"디바이스가 틀렸다" 와 "스케줄이 손해다" 를 가를 수 있다.

## 2. 미해결

### 2.1 `RCD_RD` overrun 이 실행마다 다른 뱅크에서 튄다 `[실측 — 원인 미상]`

`T_RCD=4` 에서 `RCD_RD` 가 서는 것 자체는 예상된 것이다(문서 §2 가 이상적 메모리
모델 대비 overrun 3 을 적었다). 문제는 **`max` 값의 크기와 산포**다.

위반 카운터는 **누적되고 `VIOL_CTRL[0]` 로만 지워진다.** 매 실행 전에 지우고
`emu_gemv --fill wrvec --l 1` 을 한 번씩 돌린 결과 (`max > 20` 인 뱅크만):

| 실행 | 튀는 뱅크 |
|---|---|
| 1 | b4=75 b5=74 |
| 2 | b6=43 b7=43 · b14=74 b15=74 |
| 3 | b8=90 b9=90 · b10=47 b11=47 |
| 4 | b8=25 b9=26 |
| 5 | b4=69 b5=68 |

모든 실행에서 `cnt = 1` 이고 대부분의 뱅크는 `max = 14~15` 다. 읽히는 것:

- **뱅크가 고정돼 있지 않다.** 실행마다 다른 뱅크가 튄다 — 특정 뱅크나 HBM stack 의
  고장이 아니다
- **항상 짝으로 움직인다** (b4·b5, b6·b7, b8·b9, b10·b11, b14·b15). 그 짝이 곧
  **HBM 채널 쌍**이다 (`HBM(n)_AXI → HBM(n/2)_PORT`)
- 값이 `25 ~ 90` 으로 넓다. 문서의 3 과 자릿수가 다르다

`[유도]` 채널을 공유하는 두 뱅크가 같은 순간 refresh 나 경합을 겪으면 둘 다
늦어진다 — 그러면 짝으로 움직이고 실행마다 위치가 달라지는 것이 설명된다.
확인하지 않았다.

`T_RCD` 스윕은 하지 않았다. `T_RCD=8` 이면 조용해질 것이라고 문서가 적어두었다.

### 2.2 보드가 한 번 안 답했다 — 원인 미상 `[2026-08-10 15:40]`

**확실한 것은 원인이 아니라 원인이 아닌 것이다.**

이 문서는 처음에 이것을 "한 번에 규모를 4 배 올린 탓" 으로 적었다. **그 가설은
실험으로 반증됐다** — 범인으로 지목했던 명령을 그대로 재실행했다:

| 재현 | 결과 |
|---|---|
| `emu_chain --test gemv --l 64 --g 2000 --kchunks 2 --order chunk` × 4 | **4/4 통과**. 125 MiB 업로드, 8003 ISR, 5.3 ms 커널, 32000 출력 전부 정답 |
| 더 크게 — 16003 ISR + 250 MiB 업로드 | **통과** |

전송 총량도, 프로그램 길이도, 커널 지속 시간도 아니다. 이 때문에 걸어두었던 런타임
상한(`max_isrs = 2000`)은 근거가 없어서 제거했다. IMEM 은 512 KiB = 16384 워드이고
`PROG_LEN` 이 14 비트이므로 기본값은 16383 이다.

**관측된 증상**: BAR2 memory read 전부 `0xffffffff`, config space 정상, AER 카운터
전부 0, 커널 로그 정상 크기. PCIe 에러 없이 memory space 만 죽는 형태다.
`emu_sanity` 는 이 형태에 대해 *"Programming a PDI over JTAG invalidates
enumeration; the host must remove and rescan"* 를 출력한다.

**JTAG 재프로그램이 이 증상을 만든다는 것은 맞지만, 그때 재프로그램이 있었다는
증거는 없다.** Vivado 세션(PID 2130)이 13:26 부터 붙어 있었고 그 로그에
`program_hw_devices` 가 있기는 하나, Vivado 로그에는 줄 단위 시각이 없어서 그것이
13:26 인지 15:40 인지 구분되지 않는다. PDI 의 atime(09:28)도 relatime 때문에
단서가 못 된다. **Hardware Manager 가 붙어 ILA 를 읽는 것 자체는 정상 작업이고
문제가 아니다.**

설계자는 이 시각에 다른 곳에서 보드를 동시에 쓰고 있었다고 기억한다. 그것이 가장
그럴듯한 설명이고, 그 이상으로 좁힐 근거는 없다. **단발 사건이고 재현되지 않으므로
근본 원인을 확정하지 않고 여기 기록만 남긴다.**

## 4. 도구

| 도구 | 무엇 |
|---|---|
| `emu_sanity` | CFR write/readback + 위반 CSR 창 |
| `emu_gpr_loop` | GPR DMA 왕복 |
| `emu_hbm_direct` | HBM 직접 창 도달·구분 |
| `emu_mc --read/--write` | MC normal path, 양방향 |
| `emu_gemv --fill wrvec\|copy\|both` | GEMV 한 타일, GB 채우는 두 경로 |
| `emu_ewmul [--sweep]` | EWMUL 한 조, 결과는 제3 뱅크 DRAM |
| `emu_chain --test chain\|rewind\|kchunk\|gemv` | 한 프로그램 안에서 무엇이 합성되는가 (§1.4·1.5) |
| `emu_chain --test acc\|order [--dist ...]` | 누산기 폭과 누산 순서 (§1.7) |
| `emu_chain --test split --kchunks C` | K 분할 두 배치의 속도·정확도 (§1.8) |

않았다.**
